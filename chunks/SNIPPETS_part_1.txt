## 1. MISSION — implement these three features

You must produce **drop-in TypeScript modules** plus precise integration patches (shown as
`diff`-style instructions against the snippets below, since you cannot edit files directly).

### Feature A — Persistent world per planet
When the player flies a spaceship above `SPACE_ALTITUDE` (170), the game switches from the
voxel "craft" scene to a space scene, and landing on another planet creates a **brand-new
`GameEngine`/`World`** (see §8). Returning to a previous planet currently regenerates the
base terrain from its deterministic seed but **loses every player edit** (mined blocks,
placed blocks/machines, furnace contents, camps cleared is the lone exception).

**Requirement:** mined/demolished blocks, placed blocks, machine placements, furnace
contents, and dropped-item state must be restored **per planet** when the player returns.
The base terrain must NOT be stored (it is fully deterministic from the planet seed — see
§4.4); persist a **delta/overlay** (block edits) + small entity state, replayed onto chunk
data the moment a chunk is (re)generated. Target in-memory store keyed by planet, with an
IndexedDB/localStorage back-end for cross-session survival.

### Feature B — Off-render (headless) running factory
Today the factory only "runs" as a side effect of rendering: `MachineScheduler` only ticks
machines within ~26 blocks of the player (see §4.7), `MachineRegistry.pruneDormant()` deletes
machine records 120 s after their chunk unloads, item physics sleeps beyond 24 blocks, and
when the player is on **another planet** the entire engine is disposed — nothing simulates.

**Requirement:** a headless simulation layer (`PlanetFactorySim`) with **zero Three.js
imports**, holding its own machine/item state, ticked by a **global universe clock** that
advances *all* planets — including the ones the player is not on (catch-up time-slicing when
returning, so 10 minutes away = 10 minutes of production, applied at quantized steps).
Live near-player visuals (arms, beams) must become a *view* onto this sim, not the source
of truth. Mining/smelting/conveyor progress must continue off-planet.

### Feature C — Factory must handle millions of dropped items
`ItemDropManager` hard-caps at 512 entities (`MAX_ITEMS_DEFAULT`), evicts/ despawns beyond
that, and simulates per-entity physics — it cannot scale to 1e6 items.

**Requirement:** a virtualized item layer (`ItemLedger`): items are aggregated **stacks**
`(blockId, count)` indexed by cell key, stored in typed arrays / maps, so 1e6 items cost a
few MB and updates are O(1) per cell rather than per entity. Physical `DroppedItem` entities
become a **rendering/pickup window** (bounded, e.g. ≤512) materialized from the ledger near
the player, and returned to the ledger when they leave the window. Conveyor transport at
scale must be simulated on the ledger (rate/lane based), not per-entity.

### Hard constraints & invariants (do NOT break these)
1. The world is a **toroid**: `CHUNK_SIZE=16`, `WORLD_HEIGHT=80`, `WORLD_CHUNKS=32` → the
   surface wraps every 512 blocks in X and Z. All coordinate math MUST use `wrapBlock`,
   `wrapChunk`, and `minImageF` (see §4.1) for wrap-safe delta distances.
2. Cell keys are packed by `packCell(x,y,z)`: 9 bits X | 9 bits Z | 7 bits Y. Chunk keys are
   `(cx<<5)|cz`. Reuse them; do not invent string keys for hot paths.
3. `TerrainGenerator.populateChunk` is deterministic per planet seed. Never persist raw
   generated voxels — only edits.
4. All live block edits already funnel through `World.onChanged` / the `ChangeBus`
   (`world.setBlock`, `world.destroySphere`, laser miner, fluid sim). Hook persistence there.
5. World block ids ↔ fps/item ids are mapped by `TO_FPS`/`FROM_FPS` (§4.2). The ledger stores
   **item ids** (the fps id space, what `ItemDropManager.spawn` receives).
6. Threading message: everything runs on the main thread today. Keep new code allocation-free
   in per-frame paths (pool objects like existing code does).

### 4.1 Core constants & cell keys — `src/game/core/constants.ts`, `src/game/core/cellKey.ts`

```ts
// constants.ts (complete)
export const CHUNK_SIZE = 16;
export const CHUNK_LOG2 = 4;
export const CHUNK_MASK = 15;
export const WORLD_HEIGHT = 80;
export const SEA_LEVEL = 30;
export const VIEW_DISTANCE = 5;
export const EVICT_DISTANCE = 7;
export const WORLD_CHUNKS = 32;
export const WORLD_CHUNKS_MASK = 31;
export const WORLD_SIZE = WORLD_CHUNKS * CHUNK_SIZE;        // 512
export const WORLD_HALF = WORLD_SIZE / 2;
export const wrapChunk = (c: number): number => c & WORLD_CHUNKS_MASK;
export const wrapBlock = (x: number): number => ((x % WORLD_SIZE) + WORLD_SIZE) % WORLD_SIZE;
export const wrapDelta = (d: number, m: number): number => {
  const w = ((d % m) + m) % m;
  return w > m / 2 ? w - m : w;
};
export const minImageF = (d: number): number => d - WORLD_SIZE * Math.round(d / WORLD_SIZE);
export const chunkIndex = (x: number, y: number, z: number): number =>
  (y * CHUNK_SIZE + z) * CHUNK_SIZE + x;                    // voxel index inside one chunk

// cellKey.ts (complete)
export const packCell = (x: number, y: number, z: number): number =>
  (x & 511) | ((z & 511) << 9) | ((y & 127) << 18);
export const cellX = (k: number): number => k & 511;
export const cellZ = (k: number): number => (k >>> 9) & 511;
export const cellY = (k: number): number => (k >>> 18) & 127;
export const CHUNK_BUCKETS = (WORLD_CHUNKS_MASK + 1) * (WORLD_CHUNKS_MASK + 1); // 1024
export const packChunk = (cx: number, cz: number): number =>
  ((cx & WORLD_CHUNKS_MASK) << 5) | (cz & WORLD_CHUNKS_MASK);
export const chunkOfBlock = (v: number): number => (v >> CHUNK_LOG2) & WORLD_CHUNKS_MASK;
export const chunkRadiusFor = (blockRadius: number): number =>
  (Math.ceil(blockRadius) + CHUNK_MASK) >> CHUNK_LOG2;
// file asserts: WORLD_HEIGHT > 128 would need more Y bits in packCell
```
