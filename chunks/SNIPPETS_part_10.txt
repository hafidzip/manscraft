### Item-ID migration & save-version handling (short version)

**Item ids.** Raw world coal ore now maps to a brand-new FPS id `65` (`B.RAW_COAL_ORE`); nothing previously used `65`, so no existing stored unit changes meaning by collision. FPS id `58` previously meant "raw coal drop that pretends to be processed coal" and now means strictly "processed coal": every legacy `58` unit in an inventory, ledger, or furnace slot silently becomes processed coal. That is a one-way, non-duplicating upgrade (players keep their unit count; a few raw units become processed), which is the only migration that keeps §20.7 conservation exact. `65` is added to `BLOCK_NAMES`, HUD `BLOCK_TILE`, `blockFaceTile` (→ `T.COAL_ORE`), dropped-item geometry, and any price/sell table.

**Save version.** Ore generation now depends on the local column height, so the deterministic base terrain of every planet changed. Replaying v1 block deltas over the new base would embed machines in stone or leave them floating, and v1 sim snapshots reference machine coordinates from the old base. Therefore `SAVE_VERSION` goes `1 → 2` and `PlanetStore.migrate()` archives any v1 record under `legacy:{key}` (nothing is silently deleted, and the archive is never read by the runtime) and regenerates the planet. Saves from a *newer* version are refused rather than partially read. v2 adds `crafting: CraftingTuple[]`; a v2 record missing that field is treated as an empty list. Generated ore is never written as a delta — permanent harvesting does not call `setBlock`, so an infinitely mined node adds exactly zero bytes to the save.
